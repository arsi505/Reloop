# Reloop User Journeys

This document defines the primary operational journeys within Reloop. Each journey models how business events flow through the platform and how the E-commerce Operations Manager interacts with the system.

Every journey adheres strictly to the core operational sequence:
$$\text{TRIGGER} \longrightarrow \text{DETECTION} \longrightarrow \text{USER VISIBILITY} \longrightarrow \text{RELOOP ACTION} \longrightarrow \text{VERIFICATION} \longrightarrow \text{FINAL STATE}$$

---

## Journey 1: First-Time Onboarding & Shadow Mode Progression

### Context
A growing Shopify apparel brand processing 1,800 orders/month connects Reloop for the first time. The operations team wants to identify fulfillment discrepancies without risking accidental updates to their live store or 3PL.

* **Trigger**: The Operations Manager completes the initial system connection wizard, linking Shopify and their external 3PL warehouse via API credentials.
* **What Reloop Detects**:
  - Reloop conducts an initial state comparison across the last 48 hours of orders.
  - Detects 14 historical orders with tracking numbers present at the warehouse but missing in Shopify, and 2 orders stuck in warehouse queues past the 24-hour SLA.
* **What User Sees**:
  - The **Dashboard** displays an active banner: `Operating in Shadow Mode (OBSERVE)`.
  - A summary card shows: `16 Existing Discrepancies Discovered (Read-Only)`.
  - The **Exception Inbox** populates with simulated cases tagged with `SIMULATION`.
  - Clicking any exception displays a **Recovery Preview** stating: *"In Live mode, Reloop would synchronize tracking to Shopify. In Shadow Mode, no external state is modified."*
* **Reloop Action**:
  - Reloop logs the discrepancies, calculates the brand's baseline fulfillment discrepancy rate (2.1%), and monitors inbound order webhooks without making any mutating API calls to Shopify or the 3PL.
  - After 72 hours of clean observation, Reloop prompts the user: *"Promote from OBSERVE to RECOMMEND mode to preview proposed actions in real time."*
  - The user later upgrades to `APPROVAL` mode, and finally enables `SAFE AUTO-RECOVERY` for low-risk scenarios.
* **Verification**:
  - Reloop validates read credentials continuously via lightweight heartbeat queries.
  - Reloop verifies that zero mutation requests were dispatched to Shopify or 3PL APIs during Shadow Mode.
* **Final State**:
  - Brand gains empirical confidence in Reloop’s detection accuracy; Shadow Mode transition path: `OBSERVE` $\rightarrow$ `RECOMMEND` $\rightarrow$ `APPROVAL` $\rightarrow$ `SAFE AUTO-RECOVERY`.

## Journey 2: Automatic Transient Recovery (Failure Case 1 & 2)

### Context
During peak evening order hours, the 3PL’s webhook or API experiences a brief 503 gateway timeout while Reloop is synchronizing order updates. Separately, carrier tracking is generated by ShipStation but dropped before updating Shopify.

* **Trigger**: ShipStation generates a tracking label for Shopify Order `#10492`, but the Shopify fulfillment update API returns an HTTP 500 error due to a transient Shopify platform spike.
* **What Reloop Detects**:
  - Reloop compares the ShipStation shipment record against the Shopify order state during a periodic reconciliation poll.
  - Reloop identifies that tracking `1Z9999999999999999` exists in ShipStation with status `LABEL_CREATED`, while Shopify Order `#10492` remains in `unfulfilled` state.
  - The failure is classified as **Temporary 3PL/API failure / Tracking missing in Shopify**, matching the `AUTO_RECOVER` level because order ID, line item SKUs, and destination postal codes produce a deterministic match using all required configured identifiers with no detected conflicts.
* **What User Sees**:
  - On the **Dashboard**, the `Active Problems` count increments by 1 and immediately shows status `RECOVERING`.
  - On the **Exception Inbox**, order `#10492` appears with badge `AUTO_RECOVER` and state `RECOVERING (Attempt 1/3)`.
  - The Operations Manager does not need to click or manually intervene.
* **Reloop Action**:
  - Reloop schedules an automated retry with exponential backoff and jitter (e.g., retry scheduled at +30 seconds).
  - At the retry interval, Reloop dispatches the idempotent fulfillment creation payload to Shopify using a stable logical idempotency key.
  - Shopify returns HTTP 200 OK with fulfillment ID `ful_88421`.
* **Verification**:
  - **Reloop does NOT mark the case resolved upon receiving HTTP 200.**
  - Reloop pauses 5 seconds and executes an independent GET query to Shopify (`GET /admin/api/orders/10492.json`).
  - Reloop inspects the retrieved JSON and confirms:
    1. Fulfillment status equals `fulfilled`.
    2. Tracking company matches carrier.
    3. Tracking number `1Z9999999999999999` is visibly attached to the order line items.
* **Final State**:
  - Exception status updates to `RESOLVED`.
  - **Order Timeline** logs the complete auditable history from detection to verified resolution.
  - Dashboard counter for `Auto-recovered` increments by 1.

## Journey 3: Human-Approved Recovery (Failure Case 4 & 5)

### Context
A Shopify order was placed 6 hours ago, marked paid in Shopify, but is completely missing in the warehouse 3PL management system.

* **Trigger**: A triggered provider sync followed by reconciliation detects Shopify Order `#10521` (Paid, Unfulfilled) has no matching order number, reference number, or customer email in the 3PL queue.
* **What Reloop Detects**:
  - Reloop identifies failure: **Shopify order missing at 3PL**.
  - Because re-submitting an order to a warehouse carries the financial risk of duplicate picking if the order was under a different reference, Reloop assigns recovery level `REQUIRE_APPROVAL`.
* **What User Sees**:
  - The **Dashboard** highlights `Waiting for Approval: 1`.
  - The **Exception Inbox** highlights Order `#10521` with high-contrast badge `WAITING_APPROVAL`.
  - The Operations Manager clicks the item to enter **Recovery Detail**.
  - Reloop displays the dedicated **Recovery Preview**:
    - **Problem**: Order `#10521` exists in Shopify but is absent at 3PL.
    - **Proposed Action**: Transmit order payload to 3PL fulfillment endpoint.
    - **Why This Action**: Necessary to queue physical picking and packing.
    - **Why It Is / Is Not Safe**: Checked for matching customer name and destination address in 3PL in last 48 hours—no matching records found (safe from obvious duplicate). However, human approval is required to confirm order is authorized for release.
    - **What Will Change**: New order record created at 3PL with identifier `#10521`.
    - **What Will NOT Change**: Shopify payment, line items, and customer details remain untouched.
    - **Systems That Will Be Contacted**: 3PL Ingestion API.
    - **Verification Plan**: Query 3PL API to verify order is in `PENDING_FULFILLMENT` status.
    - **Possible Risks**: If 3PL had an untracked paper batch, double fulfillment could occur.
* **Reloop Action**:
  - The user clicks **Approve Recovery**.
  - Reloop transitions state to `RECOVERING`.
  - Reloop transmits the verified order manifest to the 3PL API.
* **Verification**:
  - Reloop waits 10 seconds, then queries the 3PL's order lookup endpoint.
  - Reloop confirms the 3PL returns the order in `ACCEPTED` state with internal warehouse batch ID `WH-9041`.
* **Final State**:
  - Exception state transitions: `WAITING_APPROVAL` $\rightarrow$ `RECOVERING` $\rightarrow$ `VERIFYING` $\rightarrow$ `RESOLVED`.
  - The recovery audit log records the approving user's identity and timestamp.

## Journey 4: Blocked Duplicate-Risk Operation (Failure Case 7)

### Context
A customer service agent modified an address in Shopify, causing a second webhook to fire. Meanwhile, the 3PL had already generated a label under the original address.

* **Trigger**: A sync job attempts to evaluate unfulfilled order `#10530`.
* **What Reloop Detects**:
  - Reloop detects that while Shopify marks the order as having unfulfilled items, the 3PL records indicate an existing package with tracking `9400100000000000000000` is already staged on the shipping dock.
  - Submitting a recovery payload or retrying fulfillment would dispatch a duplicate package to the customer.
  - Reloop flags this as a **Duplicate-risk operation**.
* **What User Sees**:
  - The **Dashboard** increments `Blocked: 1` with an amber caution state.
  - In the **Exception Inbox**, the order appears with state `BLOCKED` and level `BLOCK`.
  - The **Exception Detail** shows an explicit alert: *"Automated recovery halted. High risk of duplicate physical shipment."*
  - The **Recovery Preview** shows that automated execution is disabled, providing actionable evidence (Warehouse package ID vs Shopify order status).
* **Reloop Action**:
  - Reloop actively locks any automated retry jobs associated with Order `#10530`.
  - System prevents any single-click retry until an operator completes investigation.
* **Verification**:
  - The Operations Manager contacts the warehouse floor and voids the duplicate label in the 3PL.
  - In Reloop, the user selects **Intervention Complete - Request Re-check**.
  - Reloop transitions the case to `VERIFYING` and actively queries both Shopify and 3PL endpoints to verify that the duplicate shipment record was removed and only a single valid order fulfillment state remains.
* **Final State**:
  - Only after external state convergence is independently confirmed does the case transition to `RESOLVED`.
  - If Reloop cannot verify convergence (e.g., duplicate package remains active or status is ambiguous), the case remains `BLOCKED` or transitions to `FAILED` for continued operational review.

## Journey 5: Invalid-Data Repair (Failure Case 8)

### Context
A customer enters an invalid postal code (`9021` instead of `90210`) or an unrecognized SKU variant code in a newly launched promotional bundle.

* **Trigger**: 3PL API returns a 422 Unprocessable Entity: `Invalid Postal Code for Country US`.
* **What Reloop Detects**:
  - Reloop parses the error response and identifies failure: **Invalid SKU/address/order data**.
  - Reloop assigns recovery level `BLOCK` and stops all retry loops immediately to prevent pointless API spam.
* **What User Sees**:
  - The **Exception Inbox** lists Order `#10542` with state `BLOCKED` and problem type `Invalid Order Data`.
  - The **Exception Detail** highlights the exact offending field: `shipping_address.zip: "9021"` with validation error `US ZIP codes must be 5 or 9 digits`.
* **Reloop Action**:
  - Automated retries are suspended immediately.
  - Reloop provides clear instructions: *"Correct the shipping postal code in the authoritative source system (Shopify), then return to Reloop and select Re-check & Resume."* (Reloop V1 is not an order-data editor).
  - The Operations Manager verifies the customer's true address, corrects the postal code directly in Shopify to `90210`, and returns to Reloop.
  - The user clicks **Re-check & Resume**.
* **Verification**:
  - Reloop rereads the authoritative source data from Shopify before continuing.
  - Reloop runs pre-flight validation against carrier/3PL schemas.
  - Once validated, Reloop transitions through `RECOVERING` to dispatch the payload using a stable logical idempotency key, then enters `VERIFYING`.
  - Reloop queries the 3PL's order lookup endpoint to confirm ingestion and queue placement.
* **Final State**:
  - Only upon confirmed state convergence does the exception status move to `RESOLVED`.
  - The Order Timeline documents the external data correction, source re-read, and subsequent verified resolution.

## Journey 6: Recovery Verification Lifecycle

### Context
A recovery operation has been executed (either automated or human-approved). This journey details the non-negotiable verification phase that prevents false-positive resolutions.

* **Trigger**: A recovery action (such as tracking push or warehouse submission) receives an HTTP 200 response from the target system.
* **What Reloop Detects**:
  - The HTTP request succeeded, but the actual business state inside the external system has not yet been proven.
  - Reloop transitions the case to internal state `VERIFYING`.
* **What User Sees**:
  - The **Exception Detail** and **Recovery Detail** display a prominent progress badge: `VERIFYING`.
  - A sub-label informs the user: *"Recovery executed. Verifying external systems agreement..."*
  - A verification checklist is displayed with real-time indicators:
    - [x] External API accepted payload (HTTP 200)
    - [ ] Shopify order reflects fulfillment state (Checking...)
    - [ ] Tracking number visible in customer portal
* **Reloop Action**:
  - Reloop initializes a verification poller with defined intervals (e.g., t+5s, t+15s, t+45s).
  - Reloop queries the independent GET endpoints of both Shopify and the 3PL.
  - If state has not converged after the first check (e.g., 3PL asynchronous worker lag), Reloop remains in `VERIFYING` without failing prematurely.
  - Once the GET query returns the fully matched state, verification passes.
  - If verification fails or times out after maximum attempts, Reloop transitions the case to `FAILED`, alerting the team.
* **Verification**:
  - Both data stores reflect the exact same fulfillment identifier, tracking number, and order status.
* **Final State**:
  - State transitions from `VERIFYING` to `RESOLVED`.
  - The Order Timeline displays both the execution event and the subsequent verification confirmation with timestamps.

## Journey 7: Sustained Integration Outage

### Context
The external 3PL warehouse management system experiences a 2-hour cloud outage, returning 502 Bad Gateway and connection timeouts across all API calls.

* **Trigger**: Inbound sync requests and outbound order pushes to the 3PL fail consecutively across multiple orders.
* **What Reloop Detects**:
  - Consecutive error threshold (e.g., 5 consecutive 5xx/timeout errors over 5 minutes) is exceeded for the 3PL connector.
  - Individual orders are identified as affected by **Temporary 3PL/API failure**.
* **What User Sees**:
  - The top navigation bar displays a persistent, non-intrusive operational alert: `Integration Alert: 3PL Warehouse endpoint unreachable`.
  - On the **Integrations** page, the 3PL connector status badge changes from green `HEALTHY` to red `DEGRADED / OUTAGE`.
  - The **Dashboard** reflects `Integration Health: 2/3 Healthy`.
  - In the **Exception Inbox**, related exceptions are aggregated or clearly tagged with `Integration Outage: 3PL`.
* **Reloop Action**:
  - Reloop activates connector outage handling within its retry and health-monitoring architecture:
    - Marks the integration status as `DEGRADED` or `DOWN`.
    - Suppresses aggressive retries across the affected 3PL connector.
    - Applies connector-wide exponential backoff and rate limiting.
    - Holds pending recoveries in state `OPEN` / `INVESTIGATING`.
    - Periodically executes non-mutating background health checks (e.g., lightweight status probe every 60 seconds).
* **Verification**:
  - The 3PL restores service. Reloop's background health probe confirms consecutive successful responses.
  - Reloop performs a non-mutating test read query to confirm endpoint responsiveness.
* **Final State**:
  - Integration status returns to `HEALTHY`.
  - Reloop gradually resumes queued retries with controlled pacing.
  - Exceptions progress through standard execution and verification before transitioning to `RESOLVED`.
